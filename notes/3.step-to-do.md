# Step To Do — Cat/Dog MLOps Platform

> Draft implementation plan for the end-to-end Cat/Dog classifier, organized as **separated services**.
>
> Flow: **Data Management → Training → Model Registry → Prediction → Dashboard**.
>
> Sources: `0.draft-idea.md` (business + services), `1.gptidea.md` (MLflow architecture), `2.Cat_Dog_MLOps_Project_Implementation_Guide.docx`, `3.lovable/` (UI spec).

---

## 1. Goal

Build a reproducible MLOps system as a set of **separated services**:

1. **Data Management** — a standalone service that versions image datasets, backed by **MinIO (S3) + DVC**.
2. **Training** — a service that pulls data via DVC, trains a transfer-learning model, and logs results to **MLflow**.
3. **Model Registry** — versioned `CatDogClassifier` models with a clear Production stage.
4. **Prediction** — a service that serves the **Production** model **dynamically** from the Registry.
5. **Dashboard** — the UI (already built) wired to the service APIs.

**End-to-end flow:**

```
Dataset → MinIO + DVC → Data Management API → Training → MLflow Tracking
        → Model Registry → Prediction API → Dashboard
```

## 3. Target architecture

```
                    ┌────────────────────────────────────────────────────────────┐
                    │                     Docker Compose                          │
                    │                                                            │
  Angular UI (src/ui)│                                                           │
   (Dashboard)  ─────┼──▶  Data Management API ──▶ MinIO (S3)  ◀── DVC versions  │
                    │        (FastAPI)              dataset store                 │
                    │                                                            │
                    │        ┌─────────────────────────────────────────────┐     │
                    │        │  Training API ──▶ MLflow (tracking+registry) │     │
                    │        │  (FastAPI)          ├── PostgreSQL (backend) │     │
                    │        │    DVC pull data    └── MinIO (artifacts)    │     │
                    │        └─────────────────────────────────────────────┘     │
                    │                                                            │
                    │        Prediction API ──▶ Model Registry (Production model) │
                    │        (FastAPI /predict)   loads dynamically, no hard-code │
                    └────────────────────────────────────────────────────────────┘
```

- **MinIO** plays two roles (separate buckets): S3 store for **datasets** (with DVC) and **artifact store** for MLflow.
- **DVC** versions the datasets and pairs with MinIO as its remote.
- **MLflow** = tracking + registry, backed by PostgreSQL + MinIO.
- **Prediction API** resolves `models:/CatDogClassifier/Production` — promoting a new version needs **zero code change**.

## 5. Step-by-step plan

### Step 1 — Data Management service

**Goal:** a standalone service that uploads, validates, versions, and serves image datasets. Storage is **MinIO (S3)**, versioning is handled by **DVC**.

- [x] Run **MinIO** in Docker (emulates S3): buckets `datasets` (and later `mlflow-artifacts`).
- [x] Create a data repository: `dvc init`, `dvc remote add -d minio s3://datasets/dvc` (endpoint + access key/secret to the MinIO container).
- [x] `dvc add dataset/…` on the prepared train/validation images and `dvc push` → confirm the blobs land in MinIO and only `.dvc` pointers are tracked in git.
- [x] Build the **Data Management API** (FastAPI):
  - `GET /datasets` — list dataset versions (from DVC metadata / a version index).
  - `POST /datasets` — upload a `.zip` of labelled images → store to MinIO → `dvc add` + `dvc push` → create a new version (`v1`, `v2`, …).
  - `GET /datasets/{version}` — details (image count, cat/dog split, status, MinIO object key).
  - Validation step: schema + class-balance check; expose status `uploading → validating → validated`.
- [x] Wrap DVC via subprocess (or the DVC Python API) behind the service, not in the UI.

✅ **Expected output:** curl/UI can upload a dataset, it shows up as a versioned entry, and the raw data is retrievable from MinIO via DVC (`dvc pull`).

---

### Step 2 — Training service

**Goal:** a service that pulls a dataset version from **DVC**, trains a transfer-learning model, and pushes params/metrics/artifacts/model to **MLflow (Docker)**.

- [x] Run **MLflow** in Docker (tracking server; PostgreSQL backend + MinIO artifact store — or local filesystem first, upgrade later).
- [x] Implement model code: MobileNetV2 base (frozen) + `GlobalAveragePooling2D` + `Dense(1, sigmoid)`.
- [x] Implement training that **pulls data via DVC** (`dvc pull` for the chosen dataset version), augments, and fits.
- [x] Wrap training with `mlflow.start_run()`:
  - Log **parameters**: dataset version, epochs, batch size, learning rate, image size, model name.
  - Log **metrics**: accuracy, loss, val_accuracy, val_loss.
  - Log the **model** + **artifacts** (summary, sample predictions).
- [x] Expose the **Training API**:
  - `POST /train` — start a run for a dataset version + hyper-parameters.
  - `GET /runs` — list runs with metrics/status.
- [x] Run 2–3 trainings with different hyper-parameters to produce multiple MLflow runs.

✅ **Expected output:** training reads data from DVC; each run appears in the MLflow UI with params/metrics/artifacts (e.g. Run 1 = 91%, Run 2 = 94%).

---

### Step 3 — Model Registry

**Goal:** versioned `CatDogClassifier` models with a lifecycle (`Pending → Staging → Production → Archived`).

- [ ] Register each trained model as `CatDogClassifier` (`mlflow.register_model`), producing v1, v2, v3…
- [ ] Assign stages: promote candidates to **Staging**, then the winner to **Production** (auto-demoting the old Production → Archived).
- [ ] Keep all model paths out of application code — the prediction service resolves by **name + stage**, not file path.
- [ ] Expose registry actions through an API endpoint (`POST /models/CatDogClassifier/{version}/stage`).

✅ **Expected output:** `CatDogClassifier` v1/v2/v3 with a clear Production stage; changing Production requires no code change downstream.

---

### Step 4 — Prediction service

**Goal:** `POST /predict` serves the current **Production** model dynamically.

- [ ] `model_loader.py`: `mlflow.pyfunc.load_model("models:/CatDogClassifier/Production")`.
- [ ] `main.py`: `POST /predict` — accept image upload → preprocess → infer → return `{ prediction: "cat"|"dog", confidence: 0.97 }`; optional `GET /health`.
- [ ] Verify correctness (`cat.jpg → cat`, `dog.jpg → dog`), then the **dynamic** part: promote the Production version in the Registry and call `/predict` again — no code change.

✅ **Expected output:** working FastAPI service that always serves the current Production model.

---

### Step 5 — Dashboard

**Goal:** the Angular UI (already built) talks to the real service APIs instead of mock data.

- [x] Add an API base URL + HTTP service layer in `src/ui` (keep the current `store.ts` signal shape).
- [ ] Swap mock calls for `fetch()`:

  | UI function | Endpoint (service) |
  | --- | --- |
  | `listDatasets()` / `uploadDataset(...)` | `GET, POST /datasets` (Data Management) |
  | `listRuns()` / `startTraining(cfg)` | `GET /runs`, `POST /train` (Training) |
  | `listModelVersions()` / `setModelStage(v, stage)` | `GET /models/CatDogClassifier/versions`, `POST …/stage` (Registry) |
  | `predict(image)` | `POST /predict` (Prediction) |

  > Done: Data Management (`listDatasets`/`uploadDataset`) and Training
  > (`listRuns`/`startTraining`). Pending: Registry + Prediction — their
  > services are Steps 3–4.

- [x] Keep mock data behind a dev flag (`core/env.ts` → `USE_MOCK`) so the UI runs without the backend.
- [x] Handle CORS in FastAPI (both services set `allow_origins=["*"]`).
- [ ] **Docker + reproducibility**: write `docker-compose.yml` (MinIO, MLflow+PostgreSQL, Data API, Training API, Prediction API, optional UI), plus `README.md` (setup, data, training, registry, serving, prediction).

✅ **Expected output:** every UI page reflects live backend state; uploading an image through the UI returns a real Cat/Dog prediction.

## 8. Strategy notes

- **One service at a time** — verify each service's expected output before moving to the next.
- **DVC + MinIO** give real data versioning (an upgrade over the guide's plain folders), matching the "Data Management as a separated service" requirement.
- **Start simple, then harden:** MLflow can start on the local filesystem, then move to PostgreSQL + MinIO in Step 5's Docker Compose.
- **Don't add** Kubernetes, Azure, or drift detection initially — not required by the rubric.
- The **UI is done** with a clean mock service layer, so backend services can be built and verified independently of any UI polish.
