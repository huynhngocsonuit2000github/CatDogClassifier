# 4. How "Prediction" works

This describes the Prediction service (Step 4) — how an uploaded image becomes a
`cat` / `dog` answer, and why it always uses the current Production model
without any code change.

## The one-line idea

The Prediction service does **not** store or know about a specific model file.
On every request it asks MLflow *"which `CatDogClassifier` is in Production right
now?"* and uses **that** one. So "deploy a new model" is just a click in the
Registry — nothing to redeploy in Prediction.

## The request, step by step

```
  image upload ──▶ preprocess ──▶ resolve "Production" ──▶ sigmoid ──▶ cat / dog
```

| Step | What happens | Why it has to be *just so* |
| --- | --- | --- |
| 1. Upload | browser POSTs the file (multipart) to `POST /predict` | the bytes are the input |
| 2. Preprocess | decode → RGB → resize to 160×160 (bilinear) → float32 **0–255** | must match how Training fed the model, or the answer is garbage |
| 3. Resolve | `models:/CatDogClassifier/Production` → the current winner's version | no model path in code |
| 4. Infer | MobileNetV2 → … → one sigmoid number `p` in [0,1] | `p` = "probability it's a dog" |
| 5. Answer | `p >= 0.5` → `dog`, else `cat` | `class_names = ["cats","dogs"]`, so class 1 = dog |

## Preprocessing is the trap

Training used `image_dataset_from_directory` with **no rescaling** and **no**
MobileNetV2 preprocessing, so the model learned to read **raw pixel values
(0–255)**. Prediction must do exactly the same:

| Do | Don't |
| --- | --- |
| decode as RGB, 160×160 | resize to a different size |
| keep float32 in `[0, 255]` | rescale to `[0, 1]` |
| feed it straight in | apply `mobilenet_v2.preprocess_input` |

Get this wrong and the numbers that reach the frozen MobileNetV2 trunk are in a
range it never saw, so the confidence (and sometimes the label) drift silently.

## Loading the model — and not re-downloading it

- The service loads with `mlflow.tensorflow.load_model("models:/…/v3")`
  (Training logged a Keras-3 `.keras` file under the `tensorflow` flavor —
  note: `mlflow.keras.load_model` would fail on it).
- `load_model` re-downloads the files **every call**, so the service loads once
  and keeps the model in memory, keyed by version.
- It re-checks the Production version on each request; only when that number
  changes (a promotion) does it download the new model once — usually a few
  seconds into ~15 MB of files.

So the "dynamic serving" invariant is:

> Promote `v2` → Production. The **next** `POST /predict` serves `v2`.
> No restart, no code change, no redeploy.

## The health endpoint

`GET /health` reports the model name and the currently-served version
(`model_version`), so you can confirm which model is live without making a
prediction.

## Error cases

| Situation | Response |
| --- | --- |
| no model is in Production yet | `400` "promote a version in the Registry first" |
| uploaded bytes aren't an image | `400` "could not decode image" |
| MLflow server unreachable | `503` |

## API

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/health` | liveness + served version |
| `POST` | `/predict` | multipart image → `{ prediction, confidence, model_name, model_version }` |
