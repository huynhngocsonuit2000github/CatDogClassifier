# 1. How "Upload & Validate" works

This describes the Data Management service (Step 1) — what happens when the UI
sends a dataset archive through **Upload & validate**.

## Overview

A dataset is a `.zip` archive containing images organised into two folders:

```
catsdogs.zip
├── cats/
│   ├── cat_0001.jpg
│   └── ...
└── dogs/
    ├── dog_0001.jpg
    └── ...
```

On upload, the service validates the archive, assigns it a version (`v1`, `v2`,
…), tracks it with **DVC**, and stores the bytes in **MinIO** (S3). Storage and
versioning are two separate layers:

| Layer | Tool | Role |
| --- | --- | --- |
| Object storage | MinIO (S3) | Holds the actual bytes |
| Versioning | DVC | Content-addresses + tracks each version |
| Source of truth | `index.json` | Maps logical versions → DVC files → status |

## The flow

```
UI (.zip)
  └─ POST /datasets ──▶ validate ──▶ datasets/vN/ (local)
                                        │
                            ┌───────────┴────────────┐
                            │  dvc add                │  boto3 (raw archive)
                            ▼                        ▼
                     datasets/vN.dvc           raw/vN.zip
                            │                        │
                            │  dvc push               │
                            ▼                        ▼
                     MinIO: dvc/files/md5/…     MinIO: raw/vN.zip
```

### Phase 1 — synchronous (returns `202 validating`)

1. **Validate** the archive:
   - Not a ZIP / unsafe path / missing `cats` or `dogs` folder → `422`.
   - Each image opened + `PIL.Image.verify()` for integrity; invalid ones are
     skipped (with a warning). If no valid cat or dog images remain → `422`.
2. **Assign the next version** — `index.next_version()` → `v1`, `v2`, … (kept in
   `data/.datasets/index.json`).
3. **Extract** images to the local working copy: `data/datasets/vN/`.
4. **Track with DVC** — `dvc add datasets/vN` hashes the files, stores the blobs
   in the local cache (`.dvc/cache`), and writes `datasets/vN.dvc`.
5. **Record** the version in `index.json` — status `validating`, plus the
   `.dvc` path (`datasets/vN.dvc`) and object key (`raw/vN.zip`).
6. Return `202` immediately; the version shows a pulsing `validating` badge.

### Phase 2 — background task (flips to `validated`)

1. **Upload the raw archive** to MinIO via boto3 → `raw/vN.zip`.
2. **`dvc push`** the `.dvc` file → content-addressed blobs land in MinIO under
   `dvc/files/md5/…`.
3. **Mark `validated`** in `index.json` (on any error it is marked `failed`).

The UI polls `GET /datasets` every 2s while anything is `validating`, so the
status updates on its own.

## Status lifecycle

```
validating ──▶ validated      (success)
validating ──▶ failed         (push/storage error)
```

## Where the data lives

| Place | Content |
| --- | --- |
| Local `data/datasets/vN/` | Extracted working images |
| Local `data/datasets/vN.dvc` | DVC metadata (tiny) |
| Local `data/.datasets/index.json` | Version index (source of truth) |
| Local `data/.dvc/cache/` | Local content cache |
| MinIO `raw/vN.zip` | Original archive (boto3, not DVC) |
| MinIO `dvc/files/md5/…` | Content-addressed image blobs (DVC) |
