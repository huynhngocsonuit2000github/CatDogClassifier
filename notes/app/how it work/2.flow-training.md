# 2. How "Training" works

This describes the Training service (Step 2) — what happens when the UI (or
`curl`) kicks off a training job, and how a run ends up in MLflow.

## Overview

The Training service does **not** own the data. It points at the **shared DVC
repo** that the Data Management service maintains, and for each training job it:

1. **pulls** the chosen dataset version from MinIO via DVC,
2. trains a **MobileNetV2** transfer-learning classifier,
3. **logs** the run to **MLflow** (params, metrics, model, artifacts).

| Layer | Tool | Role |
| --- | --- | --- |
| Data source | DVC (shared repo) | Materialises `datasets/vN/` on demand |
| Model | TensorFlow/Keras | Frozen MobileNetV2 → GAP → Dense(1) |
| Tracking | MLflow (Docker) | Records every run + stores the model |

## The flow

```
POST /train {dataset_version, epochs, ...}
  └─ validate version exists (shared index.json)
  └─ job id  ──▶ background thread
                    │
                    ├─ dvc pull datasets/vN.dvc   ◀── MinIO (s3://datasets)
                    ▼
              datasets/vN/  (cats/ + dogs/)
                    │
                    ├─ image_dataset_from_directory (80/20 split)
                    ├─ MobileNetV2 (frozen) + Dense(1, sigmoid)
                    ├─ model.fit(...)
                    ▼
              mlflow.start_run()
                    ├─ log_params   (version, epochs, batch, lr, image_size)
                    ├─ log_metrics  (loss, accuracy, val_loss, val_accuracy)
                    ├─ log tensorflow model
                    └─ log artifacts (metadata.json, metrics.json)
```

### The data pipeline

After `dvc pull`, `load_datasets()` in `trainer.py` reads the images with
`tf.keras.utils.image_dataset_from_directory`:

- `label_mode="binary"` turns the two folders into labels `0` (cats) and `1`
  (dogs). `class_names` carries the order, and the prediction rule is
  `sigmoid >= 0.5 → dog`.
- `image_size=(160, 160)` and the requested `batch_size`, reseeded with a fixed
  `seed=42` so every run reads the data the same way.
- A **20% validation split** (`validation_split=0.2`, `subset=training` /
  `validation`) provides the `val_*` metrics. If a version has fewer than 5
  images the split would collapse to an empty validation set, so in that case it
  trains on everything and returns `val_ds = None` (no validation metrics).

The logged metrics are the **last epoch's** values from the `fit()` history:
`loss`, `accuracy` (+ `val_loss`, `val_accuracy` when a validation set exists).

### The model

`build_model()` in `model.py` is a MobileNetV2 **transfer-learning** head:

```
MobileNetV2 (ImageNet weights, include_top=False, FROZEN)
   → GlobalAveragePooling2D   (flattens the feature map)
   → Dropout(0.2)
   → Dense(1, sigmoid)
```

- `base.trainable = False` — only the small head trains, so runs are quick and
  reuse the pretrained ImageNet features.
- Compiled with `Adam(learning_rate=…)`, `binary_crossentropy` loss, and
  `accuracy` as the metric.

### The job lifecycle (in-memory)

```
starting ──▶ pulling ──▶ training ──▶ finished      (success)
     └──────────────────────────────▶ failed        (dvc/train error)
```

`POST /train` returns `202` + `job_id` immediately; the real work runs in a
background thread. Poll `GET /jobs/{job_id}` for status; list everything with
`GET /runs` (reads back from MLflow).

## Hyperparameters

The "New run" form maps onto the `POST /train` body:

| Request field | UI field | What it means | Default |
| --- | --- | --- | --- |
| `dataset_version` | Dataset version | Which DVC-tracked snapshot to pull & train on | (from picker) |
| — | Architecture | Pretrained backbone (see note below) | `mobilenetv2` |
| `epochs` | Epochs | Full passes over the training set | UI `15` · backend `10` |
| `batch_size` | Batch size | Images processed per weight-update step | UI `32` · backend `8` |
| `learning_rate` | Learning rate | Optimizer step size | UI `0.0005` · backend `0.001` |
| `image_size` | (hidden) | Square input resolution | `160` |

- **More epochs** lift accuracy up to a point, then **overfit** (memorise rather
  than generalise). Too few → underfit.
- **Bigger batch** trains faster per epoch + smoother gradient, but uses more
  memory; smaller batch updates more noisily and sometimes generalises better.
- **Higher learning rate** converges fast but can diverge; too low stalls.

> The **Architecture** selector is currently cosmetic: `model.py` only builds
> MobileNetV2 and `trainer.py` logs `model_name: "mobilenetv2"` regardless, so
> the backend always trains MobileNetV2. The UI preselects it to match reality.

## How it talks to MLflow

The service is an MLflow **client** (the Python `mlflow` SDK); MLflow itself
runs as a separate **server** — the `mlflow` Docker container on `:5000`. They
talk over HTTP, and the client never touches the server's filesystem.

```
Training service (Python)                     MLflow server (Docker :5000)
  mlflow.set_tracking_uri(...)  ── HTTP ──▶   REST tracking API
  mlflow.start_run() / log_*     ── HTTP ──▶     ├─ metadata  → SQLite
  MlflowClient.search_runs       ◀── HTTP ──     └─ artifacts → mlartifacts
```

### The three moving parts

1. **Tracking URI** — `Settings.mlflow_tracking_uri` (default
   `http://localhost:5000`), applied with `mlflow.set_tracking_uri(...)` at
   startup (in `lifespan`) and again inside `trainer.train()`.
2. **Experiment** — `mlflow.set_experiment("catdog")` (the `MLFLOW_EXPERIMENT`
   env var). Experiments group related runs; MLflow creates `catdog` on first
   use if it doesn't already exist.
3. **Run** — `mlflow.start_run(run_name=f"{version}-mobilenetv2")` opens a run
   with a unique `run_id`. Everything logged inside the `with` block attaches to
   that run (or gets marked `FAILED` if an exception escapes).

### What gets logged (inside `trainer.train()`)

| Call | Content | Example |
| --- | --- | --- |
| `mlflow.log_params` | `dataset_version`, `model_name`, `epochs`, `batch_size`, `learning_rate`, `image_size`, `train_samples` | `epochs=10` |
| `mlflow.log_metrics` | `loss`, `accuracy` (+ `val_loss`, `val_accuracy`) as **fractions** 0–1 | `accuracy=0.80` |
| `mlflow.tensorflow.log_model(model, "model")` | the Keras model, saved as `model.keras` under `artifacts/model/` | — |
| `mlflow.log_dict` / `log_text` | `metadata.json` (class names + threshold) and `metrics.json` | — |

### Two stores: metadata vs. artifacts

MLflow keeps two kinds of data in two places, which is why the server command in
`src/docker-compose.yml` carries two flags:

| Store | Where | Server flag |
| --- | --- | --- |
| **Metadata** (runs, params, metrics, tags) | SQLite file `mlflow/mlflow.db` | `--backend-store-uri sqlite:///mlflow/mlflow.db` |
| **Artifacts** (model files, `.json`) | files under `mlflow/mlartifacts` | `--artifacts-destination /mlflow/mlartifacts` |

Both sit on the `mlflow_store` Docker volume, so they survive restarts.

### Proxied artifacts (why `--serve-artifacts`)

Because the client reaches the server over HTTP, it can't write artifact files to
the server's disk directly — that's what the artifact proxy is for:

- `--serve-artifacts` lets the server **serve** artifacts back over the REST API
  using the `mlflow-artifacts:/…` URI scheme.
- `--artifacts-destination` tells the server where on its own disk those bytes
  go (`/mlflow/mlartifacts`).
- The client only resolves its artifact root to `mlflow-artifacts:/…` when
  `--default-artifact-root` is **absent** (that default lives in MLflow's
  `resolve_default_artifact_root`). Passing a bare path there makes the client
  write artifacts to its **own** local disk instead of through the server — the
  classic "runs appear in the UI but their model files are missing" bug.

This matters downstream: `mlflow.pyfunc.load_model("runs:/<id>/model")` — and the
later Prediction service's `models:/CatDogClassifier/Production` — round-trips
through this proxy to fetch the actual model files.

### Pinned to 2.22.4

The server image and the service's `requirements.txt` both pin **MLflow 2.22.4**.
MLflow 3.x moved model storage to "logged models" and stops persisting model
files under a plain filesystem artifact root, which breaks `models:/…` URIs and
`mlflow.register_model` — both used by the Registry (Step 3) and Prediction
(Step 4) steps. 2.x keeps the classic behaviour this project depends on.

### Reading runs back (`GET /runs`)

`list_runs()` in `main.py` does **not** read the in-memory job registry — it
queries MLflow directly:

```
MlflowClient(tracking_uri=…).get_experiment_by_name("catdog")
   → search_runs(experiment_ids=[…], order_by=["start_time DESC"])
   → for each run: run_id, status, run_name, start_time, params, metrics
```

`run.info.status` is the MLflow-native status (`FINISHED` / `FAILED` / `RUNNING`),
which the UI maps to `finished` / `failed` / `running`. This is separate from the
in-memory job lifecycle: the job dict tracks the *process* (`starting →
pulling → training → finished`), MLflow tracks the *result*, and the two are
joined only by the `run_id` the job records once training completes.

## Where things live

| Place | Content |
| --- | --- |
| Shared `../data-management/data/datasets/vN/` | Pulled training images |
| Shared `../data-management/data/.datasets/index.json` | Version catalog (read-only here) |

## UI integration (Step 5)

The Angular Training page talks to this service through `TrainingApi` in
`core/api.ts`:

| UI call | Endpoint |
| --- | --- |
| `listRuns()` | `GET /runs` |
| `startTraining(cfg)` | `POST /train` |
| `getJob(id)` | `GET /jobs/{id}` |

- `AppStore.runs` holds the runs; `startTraining` POSTs, shows an optimistic
  "running" row, then polls `/jobs/{id}` until `finished`/`failed` and swaps in
  the recorded MLflow run.
- MLflow returns `accuracy`/`loss` as **fractions** (0–1) while the UI renders
  accuracy as a percentage, so `api.ts` multiplies accuracy by 100 on mapping.
- `core/env.ts` has `USE_MOCK` — set `true` to run the page on seed data with no
  backend up.
