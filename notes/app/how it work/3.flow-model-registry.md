# 3. How "Model Registry" works

This describes the Model Registry service (Step 3) — how a trained model becomes
a versioned `CatDogClassifier`, and what **Approve / Reject / Promote to
Production** actually do to it.

## Overview: logging vs. registering

Two similar-sounding things happen to every trained model, and they are
**different**:

| Concept | What it does | Where you see it |
| --- | --- | --- |
| **Logging** | Saves the model *file* under a training run | MLflow Tracking (each run's artifacts) |
| **Registering** | Adds it as a *version* of `CatDogClassifier` | Model Registry ("Models" page) |

Every run logs a model. Only runs that get **registered** appear in the
Registry. The Registry is the *curated* list — the candidates you judge and
promote.

## How a model gets registered

Two entry points, both calling `mlflow.register_model` under the hood:

1. **Automatic (new runs)** — the Training service now registers every
   successful run as the next version (`v4`, `v5`, …) right after it logs the
   model. Nothing to do.
2. **Backfill (old runs)** — `POST /models/CatDogClassifier/register` with a
   `run_id`, for runs trained before Step 3. Idempotent: registering the same
   run twice does nothing.

In both cases MLflow writes only a **pointer** in its database
("`CatDogClassifier` v4 → this run's model") and auto-increments the version.
No copy of the model file is made.

## The stage lifecycle

A version moves through stages, each guarded so you can't skip a step:

```
            Approve              Promote to production
 Pending ────────────▶ Staging ───────────────────────▶ Production
     │                   │                                   │
     │ Reject            │ Reject                 (a new winner is promoted)
     ▼                   ▼                                   ▼
 Rejected            Rejected                             Archived
                                                            (automatic)
```

The UI shows **5 stages**, but MLflow only knows **4** — so the service maps
between them:

| UI stage | MLflow stage | How |
| --- | --- | --- |
| `Pending` | `None` | every new version starts here |
| `Staging` | `Staging` | direct |
| `Production` | `Production` | promote archives the old winner |
| `Archived` | `Archived` | direct |
| `Rejected` | `Archived` + tag `rejected=true` | reject sets the tag |

That tag is how the service tells "Archived because it was rejected" apart from
"Archived because a newer version took over".

## The three buttons

These are the actions on the Registry page, and the rules for when each lights
up:

| Button | Action | Allowed from | Guard |
| --- | --- | --- | --- |
| **Approve** | `Pending → Staging` | `Pending` only | a version must be new to be approved |
| **Reject** | `Pending/Staging → Rejected` | `Pending` or `Staging` | you can reject before or after testing |
| **Promote to production** | `Staging → Production` | `Staging` only | the winner must have passed staging |

- **Approve** = "this candidate looks good, let's test it further". Move it to
  Staging.
- **Reject** = "throw this one away". It's archived, tagged as rejected, so it
  stays in the history but never becomes the live model.
- **Promote to production** = "this is the winner". It becomes the served
  model **and automatically demotes the previous Production version to
  Archived** — so there is always exactly **one** Production model at a time.
  That invariant is what Step 4 (Prediction) relies on: it just loads
  `models:/CatDogClassifier/Production` without caring which version that is.

If you send a transition the guard rejects (e.g. promote a `Pending` model), the
service returns `409 Conflict` with a message like
"`CatDogClassifier v3 is Rejected, not Pending — cannot approve`".

## Where the model lives

The Registry never copies the model file. Versions are database records
pointing back to the run where the model was logged:

| Place | Content |
| --- | --- |
| MLflow DB (`mlflow/mlflow.db`) | runs, params, metrics, **registry entries** |
| MLflow artifacts (`mlflow/mlartifacts/`) | the actual model file (`.keras`) |
| Model Registry | a pointer: "*v4 → run `…`'s model*" |

So if you register 30 versions you still have only the model files that were
actually trained — registration adds metadata, not storage.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/models` | list all versions (enriched with accuracy/loss/size) |
| `POST` | `/models/{name}/{version}/stage` | move a version's stage (guarded) |
| `POST` | `/models/{name}/register` | backfill a finished run |

`version` is the UI-style `"v3"`; the service strips the `v` for MLflow.
Consumers (the UI page, and later Prediction) only ever use **name + stage**,
never a file path.
